\section{\pizero{}}
\label{sec:model}
%=============================================================================
\pizero{} is a vision--language--action policy: camera views and an instruction
in, a chunk of future control steps out. Three stages run in sequence: a SigLIP
vision encoder, a Gemma-2B prefix that produces a K/V cache, and a Gemma-300M
action expert that denoises the action chunk against that cache.
The complete FPGA deployment executes all three stages on the accelerator and
matches the CUDA reference outcome on all ten closed-loop evaluation prompts.

The prefix accounts for three quarters of the arithmetic
(Table~\ref{tab:budget}) and sets the main compute workload. The action expert
then refines the action chunk through ten Euler steps,
$x_{t+\Delta t}=x_t+\Delta t\,v_\theta(x_t,t,\mathrm{KV}_{\text{prefix}})$,
using the cached prefix context. This maps naturally to a high-throughput
prefix stage followed by a compact, deterministic control stage.

\section{Porting}
\label{sec:port}
%=============================================================================
The \ue{} is a bit-matching ASIC IP implemented on an AMD Alveo U50 with
$8$\,GB of DRAM and operating at $366$\,MHz. Projection and MLP up/down weights
use 4-bit \iffour{}. For each quantization block, \iffour{} selects either INT4
or FP4, whichever produces the lower quantization MSE for that block. All other
weights are \bfteen{}.

%=============================================================================
\section{Quantization}
\label{sec:quant}
%=============================================================================
\subsection{\iffour{}}
\iffour{} evaluates signed INT4 and FP4 E2M1 for each $64$-element block and
keeps the lower-error representation. It therefore matches or improves on
either INT4 or FP4 alone, while using the same 4-bit storage. The block choice
is encoded in the sign of its \bfteen{} scale, so no side table is required.
Table~\ref{tab:if4} shows \iffour{} matching the best standalone format on the
synthetic extremes and exceeding both standalone formats on the \pizero{}
checkpoint groups.

\subsection{LIBERO}
\label{sec:libero}
LIBERO is a tabletop manipulation benchmark for language-conditioned policies,
scored by closed-loop task success. It provides two camera views; \pizero{}
takes three, so the third slot is zero-filled and masked.

An episode is many inferences. The simulator executes the first ten steps of
each chunk and requests the next, so one episode is a dozen or more full passes
on hardware. Table~\ref{tab:libero} compares the FPGA policy with the CUDA
reference over ten prompts with the same task definitions, initial seed, and
fixed denoise noise. This paired test measures deployment parity under matched
initial conditions; it is not intended as a benchmark-wide estimate of task
success.

\section{Throughput}
\label{sec:throughput}
%=============================================================================
Table~\ref{tab:summary} compares policy compute latency across platforms, with
the ASIC projections in bold. Table~\ref{tab:timing-fpga} showcases the
measured per-stage efficiency of the \ue{} implementation. All platforms run
batch~1 and ten denoise steps.

\textbf{FPGA.} Eight \ue{} instances run on one $8$\,GB \alveo{} at
$366$\,MHz. Times come from the engine's own cycle counters and are pure
back-to-back execution; programs are compiled once up front and that one-time
cost is excluded. The complete end-to-end run sustains a high $85\%$ of peak
compute throughput.

\textbf{ASIC projection.} The ASIC figures are derived from the measured FPGA
cycle counts. \pizero{} is heavily compute-bound, so performance scales nearly
linearly with engine count $\times$ clock across these configurations. The rows
apply $(1600\cdot N)/(366\cdot 8)$: $26.2\times$ for $N{=}48$ engines and
$35.0\times$ for $N{=}64$ at $1.6$\,GHz. Neither configuration reaches the
$104$\,GB/s memory-bandwidth limit, so memory bandwidth does not constrain
these projections.

\textbf{GPUs.} The RTX~5070 row is the measured fused
\texttt{policy.infer} path in openpi JAX/XLA. The Jetson Orin Nano row is
measured compute time from openpi PyTorch with staged \bfteen{} execution;
weight-staging time is excluded. Its deployed prefix is 968 tokens, compared
with 832 rows on the U50. The Jetson Thor row is NVIDIA's published result.
