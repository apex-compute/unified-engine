# Convolution workarounds vs the CONV hardware — op-level benchmark

Device `xdma1`, 198.32 MHz, 64 lanes, single-engine peak **25.39 GFLOPS** (clock x 128 FLOP/cycle). Generated by `conv_walkaround_bench.py`; nothing under `models/` is read or modified.


## 0. Verdict

**CONV op on dense layers: marginal compute, real memory win.** On-chip speedup 1.03x-2.20x (median 1.08x) — the matmul workarounds already run at 85-99% of peak, because an im2col conv is just a well-shaped GEMM. Preparation DRAM drops 1.5x-8.5x, since the window is never materialized. The one strong case is a first layer with few input channels (`mbv2_stem`, C_in=3, **2.20x**), where im2col wastes 4.7x the true FLOPs purely on lane padding.

**Critical fix, and the conv op cannot do it: replace the Toeplitz depthwise with tap-wise eltwise.** There is no groups/depthwise mode in the hardware, so this is a pure software change. A K-tap filter is currently stored as an L x L matrix per channel and run as a dense matmul, which executes at 0.7-1.2% of peak. Expected gain: **3.4x-6.4x per op** at a 10 s utterance (parakeet ~134 ms/stage, gemma4_e2b/e4b ~80 ms/stage), **7-16x less memory**, and it lifts the utterance-length cap the Toeplitz residency imposes. mobilenetv2 already uses this pattern (`conv2d_3x3_dw_tapwise_dram`), so it is a port, not a new kernel.

**Keep the conv feature** for low-channel first layers and for the preparation-memory saving. Do **not** expect it to fix the audio encoders: the depthwise rewrite is the higher-value and hardware-independent move, and should be done first.

## 3. Caveats that bound these numbers

- **Weight precision is not matched.** Workarounds run BF16 weights through `matmat_mul_core`; the CONV op has no BF16 weight path (`conv2d_core` takes `TYPE.IF4 / IF8 / TQ4` only). Timings compare BF16-matmul against INT4-conv, so migrating is also a quantization change — a model-quality question for an audio front end, not answered here.
- **No depthwise/grouped mode.** Emulating one with a block-diagonal dense weight would cost C x the true FLOPs (C=1024 for both audio encoders), worse than the Toeplitz it would replace.
- **Toeplitz residency caps utterance length.** At L_pad=512 the matrices alone need ~12 GiB across 24 layers, against parakeet's 3 GB reservation. This is a capability limit, not only a speed one.
- **Two more L^2 ops sit in the same parakeet block** and the conv feature does not address either: SiLU applied as an identity matmul (`2*D*L_pad^2`) and the channel-first transpose.
- **Single engine**, so these are per-op costs, not stage throughput. Toeplitz cases bench a channel subset (64 MiB budget) and scale linearly.
- **`bigvgan_conv1d` occurrences is 1**, a floor: BigVGAN runs many conv layers across its upsample stages, so its stage saving is understated.
